# PRD — IntentGuard

## Problem statement
Linux users — students, junior sysadmins, and even experienced engineers under time pressure — regularly run destructive commands (`rm -rf /`, `dd if=/dev/zero of=/dev/sda`, `chmod -R 777 /`, unintentional force-pushes touching filesystem state, misplaced wildcard deletions) without a system that understands *what the command is actually about to do* before it does it. Existing tools either (a) do nothing until it's too late, or (b) are static blocklists that don't explain *why* something is risky or offer an alternative. This means damage happens, or users disable "annoying" safety prompts entirely because they aren't informative.

## Target users
- Students and self-taught devs running Linux for the first time without a mentor looking over their shoulder.
- Junior sysadmins/DevOps engineers running commands via copy-pasted Stack Overflow snippets without fully parsing them.
- Anyone running commands generated by an LLM (increasingly common) without independently verifying them before execution — this is a growing real-world risk category.

## Core features (MVP)
- [ ] **Command interception** — a shell wrapper function that captures a command before it's handed to bash for execution. Acceptance: typing a monitored command triggers the pipeline instead of immediate execution.
- [ ] **Rule-based risk pre-filter** — regex/pattern layer that flags known-catastrophic patterns instantly (no API call needed) for the most common destructive ops. Acceptance: `rm -rf /`, `dd` to a block device, `chmod -R 777 /`, `mkfs` on mounted disks, fork bombs are caught with zero latency.
- [ ] **ML intent classifier** — a trained classifier (TF-IDF + LinearSVC) that scores ambiguous/novel commands as safe vs. risky when they don't match a hardcoded rule. Acceptance: classifier achieves meaningfully-better-than-baseline F1 on a held-out test set of labeled commands (see `eval.md`).
- [ ] **LLM explanation layer** — for anything flagged by rules or classifier, call Groq to generate: (1) a plain-English explanation of what the command will actually do, (2) the specific blast radius/impact, (3) a safer alternative command. Acceptance: explanation is generated in under ~3 seconds and is understandable to a non-expert.
- [ ] **Decision UX** — flagged commands show the explanation and require explicit confirmation (`y/N`) before executing; safe commands pass through invisibly with no added friction. Acceptance: safe commands (e.g. `ls`, `cd`, `git status`) have zero perceptible delay or interruption.

## Nice-to-have (post-MVP)
- [ ] Natural-language mode — user can also type intent in plain English and get the safe command suggested (borrows from Idea 7, only if time allows in the last 2-3 days).
- [ ] Logging/audit trail of all flagged commands for a session (useful for the "scalability to a fleet" pitch to judges).
- [ ] zsh/fish shell support in addition to bash.
- [ ] Minimal terminal-styled web demo page for the live pitch (not required, purely for presentation polish).

## Non-goals
- Kernel-level hooking or syscall interception (explicitly Track 1, out of scope).
- General-purpose AI shell replacement / full NL-to-bash translator as the *primary* deliverable.
- Production-grade multi-user deployment, RBAC, or enterprise policy management — this is a hackathon MVP, not a shipped product. The scalability story is told in the pitch, not built in code.
- Protecting against a malicious/adversarial user actively trying to bypass the wrapper (this is a safety-net tool for well-intentioned users making mistakes, not a security boundary against attackers — say this explicitly in the demo to preempt the obvious judge question).

## Success metrics
- Live demo: system correctly intercepts and explains at least 5 distinct destructive command patterns, with zero false positives on 5 common safe commands run in front of judges.
- Classifier shows a documented, measurable improvement over a naive baseline (see `eval.md`) — not just "it works," but a number that proves it.
- End-to-end latency for a flagged command (rule miss → classifier → LLM explanation) stays under ~3 seconds so the demo doesn't stall.
- Submission is understood by judges within the first 60 seconds of the pitch — meaning the "oh, it caught that" demo moment happens early, not buried in slides.

## Constraints
- Time: 14 days (11–25 Aug 2026), solo.
- Cost: Free tier only across the entire stack (Groq free tier, no paid infra). GPU is available only via free-tier Kaggle Notebooks / Google Colab — not on the local laptop.
- Tech: Local laptop is CPU-only. Any inference or component that runs *during the live demo* must be lightweight enough to run locally on CPU with no perceptible lag — this is non-negotiable for a smooth pitch. Heavier compute (e.g. training a larger/embedding-based classifier, running hyperparameter sweeps) can happen offline on Kaggle/Colab free GPU, with only the final trained artifact brought back down to run locally.
- Originality: All submissions must be original and plagiarism-free per hackathon rules — the labeled command dataset must be self-constructed/curated, not scraped verbatim from an existing security tool's ruleset without attribution and transformation.
